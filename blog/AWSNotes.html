1. Cloud Foundations

What AWS gives you: on-demand services that you can scale up and down. No need to buy and install your own servers.

Regions

  • A Region is a cluster of data centers.
  • Most services are Region-scoped.
    • Global Services — IAM, Route 53, CloudFront, WAF, etc etc.
  • How to pick a Region:
    • Compliance — legal and data-governance requirements (e.g., data residency laws).
    • Latency — proximity of the Region to your customers.
    • Available services — not every service/feature is in every Region.
    • Pricing — costs vary by Region.

Availability Zones (AZs)

  • An AZ is one or more discrete data centers with redundant power, networking, and connectivity.
  • A Region usually has 3 AZs (min 3, but can have more); a collection of AZs makes a Region.
  • AZs are isolated from each other, so a disaster in one AZ doesn't take down the others.
  • AZs are linked with high-bandwidth, low-latency networking.

Points of Presence (Edge Locations)

  • Used to deliver content to end users with low latency (the backbone for CloudFront and other edge services).

2. IAM — Identity & Access Management

Users & Groups

  • IAM is where you create users and assign them to groups.
  • The root account should not be used or shared (use it only for initial account setup).
  • Groups contain only users, no groups within groups.
  • A user can belong to multiple groups; a user doesn't have to belong to any group (allowed, but not best practice).

Permissions & Policies

  • Users and groups are assigned policies (JSON documents).
  • Apply the least-privilege principle, give only what's needed.
  • A user can have an inline policy attached directly (not via a group).

Policy Structure

A policy consists of a version, an optional ID, and one or more statements. Each statement contains:

  • Sid — optional statement identifier.
  • Effect — Allow or Deny.
  • Principal — the account/user/role the policy applies to.
  • Action — list of actions allowed or denied.
  • Resource — list of resources the actions apply to (ARNs — Amazon Resource Names).
    • An ARN uniquely identifies a resource across all of AWS (used in IAM policies, RDS, API calls, etc.).
  • Condition — optional conditions for when the policy applies.

Password Policy

  • You can enforce minimum length, uppercase/lowercase/numbers/special characters, password expiration, and prevent password reuse.
  • Helps protect against brute-force attacks.

Multi-Factor Authentication (MFA)

  • MFA = password + a device you own. You must use MFA on root account.
  • Even a stolen password is useless without the second factor.
  • MFA options:
    • Virtual MFA device (Google Authenticator, Authy).
    • FIDO security key / passkey.
    • Hardware Key Fob MFA device (and a separate variant for AWS GovCloud).

Access Methods & Access Keys

Three ways to access AWS:

  • Management Console — protected by password + MFA.
  • CLI — protected by access keys.
  • SDK — protected by access keys.

Access keys are generated in the console and managed by the user. Never share them.

  • Access Key ID ≈ username; Secret Access Key ≈ password.
  • If lost, you cannot retrieve a secret key — create a new one and deactivate the old.

CLI — interact with AWS services via shell commands; can call public APIs and script resource management.

SDK — language-specific libraries embedded in your code to manage AWS programmatically (many languages, mobile, IoT).

CloudShell — a browser-based terminal that inherits the logged-in user's credentials, defaults to your current Region, gives you persistent storage, file upload/download, and is configurable.

IAM Roles for Services

  • Some AWS services act on your behalf and need permissions — granted via IAM roles.
  • Example: an EC2 instance that needs to call AWS APIs gets an EC2 Instance Role.
  • Common roles: EC2 instance roles, Lambda function roles, CloudFormation roles.

IAM Security Tools

  • Credential Report (account-level) — lists all users and the status of their credentials.
  • Access Advisor (user-level) — shows the service permissions a user has and when they were last used (helps trim unused permissions).

Best Practices

  • Don't use the root account except for account setup.
  • One physical person = one IAM user or use IAM Identity Center for SSO.
  • Assign users to groups; assign permissions to groups.
  • Strong password policy; enforce MFA.
  • Use roles for AWS services; use access keys for programmatic access.
  • Audit with the credential report and Access Advisor.
  • Never share access keys.

3. EC2 Fundamentals

Budget Setup

  • To let an IAM user see billing, enable "IAM user and role access to billing information" from the root account.
  • Set billing notifications (e.g., max monthly cost, zero-cost) to get email alerts.
  • View "Charges by Service" to see what's costing the most.

What is EC2?

EC2 (Elastic Compute Cloud) is AWS's most popular service. The ecosystem includes:

  • Renting virtual machines (EC2)
  • Storing data on virtual drives (EBS)
  • Distributing load across machines (ELB)
  • Scaling with Auto Scaling Groups (ASG)

Sizing & Configuration

You choose: OS (Windows/Linux/Mac), compute (CPUs/cores), RAM, storage (EBS/EFS network-attached or EC2 Instance Store), network card (speed, public IP), firewall rules (security groups), and a bootstrap script (EC2 User Data).

EC2 User Data

  • A bootstrap script that runs once at first boot as the root user.
  • Used to install updates/software, download files, etc.

Instance Types

Naming convention example — m5.2xlarge: m = instance class, 5 = generation, 2xlarge = size.

  • General Purpose — balance of compute/memory/networking (web servers, code repos).
  • Compute Optimized — heavy compute (media transcoding, batch processing, HPC, ML, gaming servers).
  • Memory Optimized — large datasets in RAM (high-performance DBs, in-memory DBs, real-time big-data processing).
  • Storage Optimized — high sequential read/write to large local datasets (OLTP, NoSQL/relational DBs, in-memory caches like Redis, data warehousing).

Hands-On Notes

  • You need a key pair to SSH in (Windows 10+ uses OpenSSH .pem; older Windows uses PuTTY .ppk).
  • User Data goes in the Advanced section at launch.
  • Stopping/starting an instance can change the public IPv4, but the private IP stays the same.

Security Groups

  • Act as a firewall controlling traffic to/from the EC2 instance.
  • Allow rules only; can reference by IP range or by another security group.
  • Regulate ports, authorized IP ranges (IPv4/IPv6), inbound and outbound traffic.
  • Can attach to multiple instances; locked to a Region/VPC combination.
  • Inbound default = blocked; outbound default = allowed.
  • Connection refused = application error; timeout = security group / network issue.
  • Best practice: keep one separate security group for SSH access.

SSH Overview

  • SSH works on Mac, Linux, Windows 10+. PuTTY for older Windows.
  • EC2 Instance Connect works for most Linux AMIs.
  • EC2 Instance Connect Endpoint where you can connect without bastion host, instance's public IP, and/or VPC internet.
  • Never put IAM access keys on an EC2 instance — attach an IAM role instead.

Purchasing Options (exam-heavy)

  • On-Demand — short, unpredictable workloads. Pay by second (Linux/Windows) or by hour (others). Highest cost, no commitment, no upfront.
  • Reserved (1 or 3 yr) — long, steady-state workloads. Specify instance type, Region, tenancy, OS. Convertible RIs allow changing type (lower discount). Pay all/partial/no upfront. Can buy/sell on the RI Marketplace.
  • Savings Plans (1 or 3 yr) — commit to a $/hour amount. Same discount as RIs; usage beyond the plan billed on-demand. Locked to instance family and Region (flexible on size, OS, tenancy).
  • Spot Instances — cheapest, but can be reclaimed anytime if the spot price exceeds your max. Great for fault-tolerant workloads. Not for critical jobs or databases.
  • Dedicated Host — a whole physical server; control instance placement. For compliance or BYOL (server-bound licenses). Pay on-demand or reserved.
  • Dedicated Instances — dedicated hardware, but may share with other instances in the same account.
  • Capacity Reservations — reserve capacity in a specific AZ for any duration; charged on-demand even if unused; no discount on its own (combine with RIs/Savings Plans for discounts).

Public IPv4 Charges

  • All public IPv4 addresses cost $0.005/hour.
  • A load balancer uses one public IPv4 per AZ (not free). RDS gets one public IPv4 (not free). IPv6 is fine (no charge).

Spot Instances Deep Dive

  • Define a max spot price.
  • A spot request includes: max price, desired count, launch spec, request type (one-time or persistent).
  • To stop spot instances you must first cancel the spot request, then terminate the instances.

Spot Fleets

  • A set of Spot instances (+ optional On-Demand) that tries to meet target capacity within price constraints.
  • Define launch pools (instance type, OS, AZ); the fleet picks the best pools.
  • Allocation strategies: lowestPrice (cost-optimized), diversified (availability), capacityOptimized, priceCapacityOptimized (best — highest capacity then lowest price).

Private vs Public IP (IPv4)

  • IPv4 example 1.160.10.240; IPv6 example 3ffe:1900:4545:3:200:f8ff:fe21:67cf.
  • IPv4 allows ~3.7 billion addresses (running out); IPv6 is newer and vast.
  • Public IP — reachable across the internet, must be globally unique.
  • Private IP — used in a private network (LAN); only specific ranges allowed; unique within the network.

Elastic IPs

  • Public IP changes on stop/start. For a fixed public IP, use an Elastic IP.
  • Yours until you release it; attachable to one instance at a time; you can remap it to mask failures.
  • Limit of 5 per Region.
  • Best practice: avoid Elastic IPs — use a random public IP + DNS, or front with a load balancer.

Placement Groups

  • Cluster — instances packed in one AZ for low latency / 10 Gbps. Great for fast big-data jobs and HPC; risk: whole group lost if the AZ fails.
  • Spread — instances on distinct hardware (max 7 per AZ). For critical apps needing high availability.
  • Partition — instances spread across partitions (distinct racks) within AZs; scales to 100s of instances. For Hadoop/HDFS, HBase, Cassandra, Kafka.

Elastic Network Interfaces (ENI)

  • A virtual network card giving an EC2 instance network access.
  • Can have a primary + secondary private IPv4s, one Elastic IP per private IPv4, one public IPv4, security groups, and a MAC address.
  • Bound to a specific AZ; can be detached and attached to other instances.

EC2 Hibernate

  • Stop = data kept on EBS; Terminate = EBS destroyed (by default).
  • Hibernate dumps RAM to the EBS root volume so boot/resume is faster.
  • Requirements: RAM < 150 GB, EBS root must be encrypted, not for bare metal, can't hibernate more than 60 days.

4. EC2 Instance Storage (EBS, EFS, AMI)

EBS Volumes (Elastic Block Store)

  • A network drive attached to a running EC2 instance; data persists after termination (if not set to delete).
  • Mounted to one instance at a time (except Multi-Attach); locked to one AZ.
  • Capacity (GB) and IOPS defined in advance; one instance can have multiple volumes.
  • Can be created unattached; delete-on-termination is configurable (default ON for root, OFF for others).

EBS Snapshots

  • Point-in-time backups; recommended to detach the volume first.
  • Can be copied across AZs/Regions (restore to another AZ/Region to move a volume).
  • Snapshot Archive — cheaper tier; 24–72 hr to restore.
  • Recycle Bin — retain deleted snapshots (1 day to 1 year).
  • Fast Snapshot Restore (FSR) — forces full initialization; expensive.

AMI (Amazon Machine Image)

  • A customized image (own software, OS, config) for faster boot/configuration.
  • Region-specific (copyable across Regions).
  • Launch from a public AWS AMI, your own AMI, or a Marketplace AMI.
  • Process: launch & customize → stop → build AMI → launch new instances from it.

EC2 Instance Store

  • A physical disk attached to the host — high IOPS/throughput, but ephemeral.
  • Data is lost on stop/terminate (and on hardware failure — you back it up).
  • Good for buffer, cache, scratch, temporary content; not long-term storage.

EBS Multi-Attach (io1 / io2)

  • Attach the same volume to up to 16 EC2 instances, all with read/write.
  • All instances and the volume must be in the same AZ; requires a cluster-aware file system.
  • Use case: high-availability clustered Linux apps that manage concurrent writes.

EBS Encryption

  • Encrypts data at rest, in flight (instance↔volume), all snapshots, and all volumes created from snapshots.
  • Low latency; uses KMS (AES-256).
  • To encrypt an unencrypted volume: snapshot it → copy the snapshot with encryption enabled → restore.

Amazon EFS (Elastic File System)

  • Managed NFS that can be mounted on many EC2 instances across AZs.
  • Scalable, highly available, pay-per-use (more expensive), auto-scaling — no capacity planning.
  • POSIX file system; uses NFSv4.1; controlled via security groups; Linux only (not Windows).
  • Encryption at rest via KMS.
  • Use cases: content management, web serving, data sharing, WordPress.

EFS Performance & Throughput

  • Performance mode (set at creation): General Purpose — default, lowest latency, now recommended for all workloads. Max I/O is previous-generation (higher latency) and isn't supported with Elastic throughput or One Zone.
  • Throughput mode: Bursting (scales with file-system size), Provisioned (fixed regardless of size), Elastic (auto-scales up/down with the workload — best for unpredictable/spiky traffic; scales to tens of GiB/s).

EFS Storage Classes

  • Standard (frequent), Infrequent Access (EFS-IA) (retrieval cost, cheaper storage), Archive (rarely accessed, ~50% cheaper). Use lifecycle policies to move files between tiers.
  • Availability: Standard = Multi-AZ (prod); One Zone = single AZ (dev), backup on by default, IA-compatible — over 90% cost savings.

EBS vs EFS

  • EBS: one instance, locked to AZ; gp2 IOPS scales with size, gp3/io1 scale independently. Migrate across AZ via snapshot → restore. Root volumes delete on termination by default.
  • EFS: mount on 100s of instances across AZs; share files; Linux only (POSIX); higher price but storage tiers save money.

5. High Availability & Scalability — ELB & ASG

Scalability & High Availability

  • Vertical scaling — make an instance bigger.
  • Horizontal scaling — add more identical instances (scale out = add, scale in = remove). Requires a distributed system; common for web apps. Used by ASGs and load balancers.
  • High Availability — run across at least 2 AZs so you survive losing a data center.

Load Balancing

A server (or set) that forwards traffic to downstream EC2 instances and evens out load.

  • Pros: spread load, single point of access, handle instance failures, health checks, SSL termination, stickiness via cookies, multi-AZ HA, separate public/private traffic.

Elastic Load Balancer (ELB)

  • Managed by AWS (upgrades, maintenance, HA); integrated with AWS services; provides a static DNS name.
  • Cheaper to run your own, but then you manage it and lose integrations.

Health Checks

  • ELB checks each instance via a port + route; a non 200 response means no traffic is sent there.

Types of Load Balancer

  • Classic Load Balancer (CLB) — deprecated.
  • Application Load Balancer (ALB) — HTTP, HTTPS, WebSocket (Layer 7).
  • Network Load Balancer (NLB) — TCP, TLS, UDP (Layer 4).
  • Gateway Load Balancer (GWLB) — Layer 3.

ELBs can be internal (private) or external (public).

Load Balancer Security Groups

  • Users reach the LB from anywhere; the EC2 instances allow traffic only from the LB's security group (source is a security group, not an IP range).

Application Load Balancer (ALB) — Layer 7

  • Load-balance HTTP across machines (target groups) and across apps on the same machine (containers).
  • Supports HTTP/2, WebSockets, redirects.
  • Routing rules: by URL path (/users vs /posts), by hostname (one.example.com), by query string / headers.
  • Great for microservices and containers (Docker, ECS); supports port mapping to dynamic ECS ports.

ALB Target Groups: EC2 instances (HTTP), ECS tasks (HTTP), Lambda functions (HTTP→JSON event), private IP addresses. ALB can route to multiple target groups; health checks are at the target-group level.

Good to know: fixed hostname; app servers don't see the client IP directly — the true client IP is in X-Forwarded-For (X-Forwarded-Port, X-Forwarded-Proto for the rest).

Network Load Balancer (NLB) — Layer 4

  • TCP/UDP; extremely high throughput; ultra-low latency.
  • One static IP per AZ; supports assigning Elastic IPs.
  • Target groups: EC2 instances, private IP addresses, or an ALB (NLB→ALB gives a static IP + HTTP rules). Health checks support TCP, HTTP, HTTPS.

Gateway Load Balancer (GWLB) — Layer 3

  • Deploy/scale/manage 3rd-party network virtual appliances (firewalls, IDS/IPS).
  • Traffic flows: user → GWLB → 3rd-party appliances → GWLB → application.
  • Combines a transparent network gateway + load balancing. Uses the GENEVE protocol on port 6081.
  • Target groups: EC2 instances, private IP addresses.

Sticky Sessions (Session Affinity)

  • Same client keeps connecting to the same instance, via cookies with a controllable expiration.
  • Saves session data (e.g., login) but can imbalance load.
  • Cookie names:
    • Application-based — custom cookie: generated by the target; don't use reserved names AWSALB, AWSALBAPP, AWSALBTG.
    • Application-based — application cookie: generated by the LB, named AWSALBAPP.
    • Duration-based: generated by the LB — AWSALB (ALB) / AWSELB (CLB).

Cross-Zone Load Balancing

  • On: traffic is spread evenly across all instances in all AZs.
  • Off: traffic is split evenly per AZ first, so an AZ with fewer instances can be overloaded.
  • ALB: enabled by default (can disable at target-group level). NLB/GWLB: disabled by default (enabling incurs inter-AZ data charges).

SSL / TLS Certificates

  • Encrypt traffic between client and LB (in-flight encryption).
  • SSL is older; TLS is the modern version (people still say "SSL").
  • Public certs are issued by Certificate Authorities and have an expiration you must renew.
  • LB uses an X.509 cert; manage with ACM or upload your own.
  • HTTPS listener: specify a default cert, optionally add more for multiple domains; clients use SNI to pick the hostname; you can set a security policy for legacy SSL/TLS.

Server Name Indication (SNI)

  • Lets the server load the correct cert for the requested hostname when multiple certs share a listener.
  • Works for ALB, NLB, and CloudFront only — not CLB.

Connection Draining / Deregistration Delay

  • Connection Draining (CLB) / Deregistration Delay (ALB & NLB).
  • Gives in-flight requests time to finish when an instance is deregistering/unhealthy; stops new requests to it.
  • 1–3,600 seconds (default 300); can disable (0). Use a low value for short requests.

Auto Scaling Group (ASG)

  • Adds/removes instances based on load (scale out / scale in); has min, desired, max.
  • New instances register with the LB; unhealthy instances are terminated and replaced.
  • Launch Template includes: AMI + instance type, User Data, EBS volumes, security groups, SSH key pair, IAM roles, network/subnet info, LB info.

Scaling Policies

  • Dynamic Scaling:
    • Target Tracking — simplest (e.g., keep average CPU at 40%).
    • Simple / Step Scaling — react to CloudWatch alarms (e.g., +2 when CPU > 70%).
  • Scheduled Scaling — for known patterns (e.g., everyone logs in at 4 PM).
  • Predictive Scaling — scale ahead of time based on historical load.

Good metrics to scale on: CPU utilization, request count per target, average network in/out, or any custom CloudWatch metric.

Scaling Cooldowns

  • After a scaling activity, a default 300-second cooldown blocks new scaling.
  • Use a ready-to-use AMI to reduce configuration time and serve requests faster.

6. RDS, Aurora & ElastiCache

RDS Overview

  • Managed relational database service (SQL). AWS manages these engines: PostgreSQL, MySQL, MariaDB, Oracle, Microsoft SQL Server, IBM DB2, Aurora.
  • Benefits: automated provisioning/OS patching, continuous backups + point-in-time restore, monitoring dashboards, read replicas, Multi-AZ for DR, maintenance windows, vertical/horizontal scaling, storage on EBS.
  • Con: no SSH access (except RDS Custom).

Storage Auto Scaling

  • Increases storage dynamically when: free storage < 10% of allocated, low storage lasts ≥ 5 min, and ≥ 6 hr since last modification. Set a max threshold. Supports all engines.

Read Replicas (read scalability)

  • Read-only copies, asynchronous replication (eventually consistent); up to 15.
  • Within AZ, cross-AZ, or cross-Region; a replica can be promoted to its own DB.
  • App must update its connection string to use replicas (SELECT statements only).
  • Network cost: free within a Region; cross-Region replication incurs cost.

Multi-AZ (Disaster Recovery)

  • Synchronous replication to a standby in another AZ under one DNS name; automatic failover.
  • Increases availability; not for scaling (no reads/writes from the app on the standby).
  • Read replicas can themselves be Multi-AZ for DR.
  • Single-AZ → Multi-AZ is a zero-downtime operation (snapshot taken, restored in a new AZ, then synced).

RDS Custom

  • For Oracle and Microsoft SQL Server with OS + database customization (patches, native features, SSH/SSM access to the underlying EC2).
  • Turn off Automation Mode during customization (and consider a snapshot first).

Amazon Aurora

  • AWS-proprietary; compatible with PostgreSQL and MySQL.
  • ~5× faster than MySQL on RDS, ~3× faster than PostgreSQL on RDS.
  • Storage auto-grows (10 GB → 128 TB); up to 15 replicas; instantaneous failover (< 30 s).
  • Costs more but is efficient.

High Availability & Read Scaling: - 6 copies of data across 3 AZs: need 4/6 to write, 3/6 to read; self-healing; storage striped across 100s of volumes. - One master takes writes; failover < 30 s; up to 15 read replicas (auto-scalable), any of which can become master; replicas support cross-Region replication.

DB Cluster endpoints: a Writer Endpoint and a Reader Endpoint (load-balances replicas). Custom Endpoints can target a subset of replicas (e.g., the larger ones for heavy queries).

Features: auto failover, backup/recovery, isolation/security, compliance, push-button scaling, auto patching (zero downtime), advanced monitoring, Backtrack (restore to any point in time via transaction logs, without backups).

Aurora Serverless — auto instantiation + scaling based on usage; no capacity planning; pay per second. Good for infrequent, unpredictable workloads, and production workload.

Global Aurora — 1 primary Region (read/write) + up to 5 secondary read-only Regions (replication lag < 1 s); up to 16 read replicas per secondary Region; promote a secondary in < 1 min for DR.

Aurora Machine Learning — SQL-based predictions via SageMaker (any model) and Comprehend (sentiment). Use cases: fraud detection, ad targeting.

Babelfish for Aurora PostgreSQL — runs MS SQL Server (T-SQL) queries on Aurora PostgreSQL with little/no code change; migrate via AWS SCT + DMS.

Backups

  • RDS: daily full backup + transaction logs every 5 min; retention 1–35 days (0 disables). Manual snapshots kept as long as you want (cheaper than running the DB).
  • Aurora: automated backups 1–35 days (can't disable) with point-in-time recovery; manual snapshots kept indefinitely.

Restore Options

  • Restoring a snapshot creates a new DB.
  • MySQL RDS from S3: back up on-prem DB → store on S3 → restore to a new RDS instance.
  • MySQL Aurora from S3: back up with Percona XtraBackup → store on S3 → restore to a new Aurora cluster.

Aurora Database Cloning

  • Create a new cluster from an existing one using copy-on-write (shares the data volume initially; new storage allocated only on writes). Faster and cheaper than snapshot + restore.

Security

  • At rest: master and replicas encrypted at launch via KMS. If the master isn't encrypted, replicas can't be either. To encrypt an unencrypted DB: snapshot → restore encrypted.
  • In flight: TLS-ready by default (use the AWS TLS root cert).
  • IAM authentication — connect with IAM roles instead of username/password.
  • Security groups for network access; no SSH (except RDS Custom); audit logs to CloudWatch.

RDS Proxy

  • Managed proxy that pools and shares DB connections (instead of every connection hitting the DB).
  • Serverless, auto-scaling, highly available; reduces failover time by 66%.
  • Supports RDS (MySQL, PostgreSQL, MariaDB, MS SQL Server) and Aurora (MySQL, PostgreSQL).
  • Enforces IAM auth, stores credentials in Secrets Manager.
  • Never publicly accessible, must be accessed from within a VPC.

ElastiCache Overview

  • Managed Redis or Memcached — in-memory data stores with very high performance and low latency.
  • Valkey — can be used with Redis OSS and Memcached.
  • Reduces load on databases for read-heavy workloads; helps make apps stateless.
  • AWS handles OS/patching, optimization, setup, monitoring, recovery, backups.
  • Requires application code changes to use the cache.

DB Cache pattern: check the cache first (hit → return); on a miss, query RDS and store the result in the cache.

Redis vs Memcached

Redis Memcached
Multi-AZ / failover Yes (auto-failover) No
Replication (read replicas) Yes No
Persistence / backup & restore Yes (AOF) No
Data structures Sorted sets, lists, etc. Simple key/value only
Sharding Yes (Cluster Mode) Yes (multi-node)
Multi-threaded No Yes

Caching Patterns

  • Lazy Loading — cache read data; data can become stale.
  • Write-Through — update the cache whenever the DB is written (no stale data).
  • Session Store — store temporary session data with TTL.

Redis Use Case — Leaderboards

  • Gaming leaderboards are computationally complex; Redis Sorted Sets guarantee uniqueness + ordering, ranking each new element in real time.

Cache Security

  • ElastiCache supports IAM authentication for Redis; IAM policies otherwise apply only at the AWS API level.

7. Route 53

What is DNS

    Translates human-friendly hostnames to IP addresses using a hierarchical naming structure, the backbone of the internet.

Terminology

  • Domain Registrar — Route 53, GoDaddy, etc.
  • DNS Records — A, AAAA, CNAME, NS, …
  • Zone File — holds DNS records.
  • Name Server — resolves DNS queries (authoritative or non-authoritative).
  • TLD — .com, .org, .net. SLD — amazon.com, google.com.

How DNS Works

Browser asks the local DNS server → Root DNS → TLD DNS → SLD DNS → answer is cached locally (per TTL) and returned to the browser, which loads the web server.

Amazon Route 53

  • Fully managed, scalable, authoritative DNS (you control the records).
  • Also a domain registrar; can health-check resources.
  • The only AWS service with a 100% availability SLA.

Records

Each record has: domain/subdomain name, record type, value, routing policy, and TTL. Must-know types:

  • A — hostname → IPv4.
  • AAAA — hostname → IPv6.
  • CNAME — hostname → another hostname (target must have an A/AAAA record); cannot be used at the zone apex (root) — e.g., not example.com, but www.example.com is fine.
  • NS — name servers for the hosted zone; control how traffic is routed.
  • Advanced: CAA, DS, MX, NAPTR, …

Hosted Zones

  • A container for records defining how to route traffic for a domain and its subdomains.
  • Public Hosted Zone — internet routing (public domains).
  • Private Hosted Zone — routing within VPC(s); only queryable from inside those VPCs.
  • Cost: $0.50/month per hosted zone.

TTL (Time To Live)

  • Clients cache the answer for the TTL duration. Low TTL = fresher data but more queries (higher cost); high TTL = fewer queries but staler data.

CNAME vs Alias

  • CNAME — points a hostname to another hostname; non-root domains only.
  • Alias — points a hostname to an AWS resource (e.g., a load balancer); works for root and non-root domains; free; supports native health checks.

Routing Policies

  • Simple — route to a single resource; can return multiple values (client picks one at random); with Alias, only one AWS resource; no health checks.
  • Weighted — assign relative weights (need not sum to 100); records share name/type; supports health checks. Use for load balancing across Regions or canary testing. Weight 0 stops traffic to that record (if all are 0, all are returned equally).
  • Failover (Active-Passive) — (filled in) associate the primary record with a health check; if it fails, Route 53 returns the secondary. The secondary can have its own health check; Route 53 returns the healthy record.
  • Latency-based — route to the Region with the lowest latency for the user; supports health checks; you typically specify the Region per record.
  • Geolocation — route by user location (continent, country, or US state — most precise match wins). Create a default record for no-match. Use cases: localization, content restriction, load balancing. Can use health checks.
  • Geoproximity (Route 53 Traffic Flow) — route by geographic location of users and resources, with a bias to shift more/less traffic (1 to 99 = more; -1 to -99 = less). Resources can be AWS (specify Region) or non-AWS (lat/long).
  • IP-based — route by client IP; you supply CIDR→endpoint mappings. Use cases: optimize performance, reduce network cost.
  • Multi-Value Answer — return multiple values/resources (up to 8 healthy records per query), with health checks; not a substitute for an ELB.

Health Checks

  • HTTP health checks are for public resources only; associate them with records for automatic DNS failover.
  • Three kinds: monitor an endpoint, monitor other health checks (calculated), monitor CloudWatch alarms.
  • Integrated with CloudWatch metrics.

Monitoring an endpoint: ~15 global health checkers; healthy/unhealthy threshold = 3 (default); interval 30 s (or 10 s, more expensive); protocols HTTP/HTTPS/TCP. If > 18% of checkers report healthy, the endpoint is healthy. Passes on 2xx/3xx; can match text in the first 5,120 bytes. Allow Route 53 checker IPs through your firewall.

Calculated health checks — combine up to 256 child checks with AND/OR/NOT; specify how many children must pass. Use case: maintenance without failing all checks.

Private hosted zones — checkers are outside the VPC and can't reach private endpoints; instead create a CloudWatch metric + alarm and a health check that watches the alarm.

Registrar vs DNS Service

  • A registrar usually provides DNS, but you can use Route 53 with a 3rd-party registrar (e.g., GoDaddy): create a Route 53 hosted zone, then set the Route 53 name servers in the registrar's NS records.

Hybrid DNS & Resolver Endpoints

  • By default Route 53 Resolver resolves: EC2 instances, private hosted zone records, and public name servers.
  • To resolve between a VPC and other networks (peered VPCs, on-prem via Direct Connect/VPN):
    • Inbound Endpoint — let on-prem resolvers forward queries to Route 53 Resolver (resolve AWS resources / private hosted zones).
    • Outbound Endpoint — Route 53 Resolver conditionally forwards queries to your DNS resolver, using Resolver Rules.
  • Endpoints associate with VPCs in the same Region; create in two AZs for HA; each supports 10,000 queries/sec per IP.

Resolver Rules: - Conditional Forwarding — forward a domain (and subdomains) to a target IP. - System Rules — selectively override forwarding behavior. - Auto-defined System Rules — how internal domains resolve. - Most specific match wins; rules can be shared across accounts via AWS RAM.

8. Elastic Beanstalk

Elastic Beanstalk

  • Upload your code; Beanstalk provisions EC2, load balancing, auto scaling, health monitoring, networking (you can still configure everything).
  • Components: Application (collection of components), Application version, Environment (runs one app version at a time).
  • Environment tiers: Web Server (ELB → ASG) and Worker (messages from an SQS queue → worker EC2 instances). Multiple environments (dev/test/prod).
  • Deployment modes: single instance (dev/test), high availability with load balancer (prod).

9. Amazon S3

Use Cases

Backup/storage, disaster recovery, archive, hybrid cloud storage, application/media hosting, data lakes & big-data analytics, software delivery, static websites.

Buckets & Objects

  • Files = objects, stored in buckets. Bucket names are globally unique; buckets are defined at the Region level.
  • Naming: no uppercase, no underscores; 3–63 chars; not an IP; start with a lowercase letter/number; not prefixed xn--; not suffixed -s3alias.
  • Objects: key = full path (prefix + object name), e.g., s3://my-bucket/folder1/folder2/file.txt. Max object size 5 TB; anything > 5 GB must use multipart upload. Objects have metadata, tags, and a version ID (if versioning is on).

Security

  • User-based — IAM policies define which API calls a user can make.
  • Resource-based — bucket policies (bucket-wide, allow cross-account), object ACLs (fine-grained), bucket ACLs (less common).
  • An IAM principal can access an object if (its IAM permissions OR the resource policy allow it) AND there's no explicit deny.
  • Encryption with keys.

Common patterns: public access via bucket policy; user access via IAM policy; EC2 access via IAM role; cross-account via bucket policy.

Static Website Hosting

  • S3 can host static sites accessible on the internet. Give public access or you'll get 403 Forbidden.

Versioning

  • Enabled at the bucket level; same-key overwrite creates a new version. Great for rollback and protection against accidental deletes.
  • Files before versioning have version null; suspending versioning doesn't delete existing versions.

Replication (CRR & SRR)

  • Cross-Region and Same-Region replication. Requires versioning on source and destination; can be cross-account; copying is asynchronous; needs proper IAM permissions.
  • Use cases: CRR — compliance, lower latency, cross-account; SRR — log aggregation, prod↔test.
  • Only new objects replicate; use S3 Batch Replication for existing/failed ones.
  • Delete markers can be replicated; deletes with a version ID are not replicated. No chaining (replication isn't transitive).

Durability & Availability

  • Durability: 99.999999999% (11 nines) across multiple AZs — same for all classes (~1 object lost per 10,000 every 10,000 years).
  • Availability: varies by class (how often the service is reachable).

Lifecycle Rules

  • Transition actions — move objects to another class (e.g., Standard-IA after 60 days, Glacier after 6 months).
  • Expiration actions — delete objects after a time (logs after 365 days, old versions, incomplete multipart uploads).
  • Scope rules by prefix or tags.

S3 Analytics — Storage Class Analysis

  • A daily CSV report suggesting the right class. Doesn't work for One Zone-IA or Glacier; 24–48 hr to start.

Requester Pays

  • Normally the bucket owner pays storage + transfer. With Requester Pays, the (authenticated) requester pays transfer; owner still pays storage.

Event Notifications

  • Events: object created/removed/replicated, etc.; filter by name (e.g., *.jpg).
  • Targets: SNS, SQS, Lambda — each needs a resource access policy allowing S3 to write (not an IAM role).
  • Use case: generate thumbnails. Usually delivered in seconds (sometimes a minute+).

With EventBridge — all events go to EventBridge for advanced JSON filtering, multiple destinations, and routing to 18+ AWS services.

Performance

  • Auto-scales: at least 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests/sec per prefix; unlimited prefixes (100–200 ms latency).
  • Multipart upload — recommended > 100 MB, required > 5 GB; parallelizes uploads.
  • Transfer Acceleration — send to a nearby edge location, then over AWS's private network to the bucket; works with multipart.
  • Byte-Range Fetches — parallelize GETs by byte range; better resilience; fetch partial data (e.g., a header).

Batch Operations

  • Bulk actions in one request: modify metadata/properties, copy between buckets, encrypt, modify ACLs/tags, restore from Glacier, invoke Lambda per object.
  • A job = object list + action + optional parameters; manages retries, progress, notifications, reports. Use S3 Inventory + Athena to build the object list.

Storage Lens

  • Org-wide analysis to optimize storage and spot anomalies; aggregates by org/account/Region/bucket/prefix; default or custom dashboards; can export metrics daily to a bucket.
  • Metric categories: Summary, Cost-Optimization, Data-Protection, Access-Management, Event, Performance, Activity, Detailed Status Code.
  • Free: ~28 days of usage, queryable for 14 days. Paid: advanced metrics, CloudWatch publishing, prefix aggregation, 15 months of data.

10. Amazon S3 Security

Object Encryption

  • SSE-S3 (default) — keys managed by AWS; AES-256; header x-amz-server-side-encryption: AES256. On by default for new buckets/objects.
  • SSE-KMS — keys in AWS KMS; you control + audit via CloudTrail; header x-amz-server-side-encryption: aws:kms. Limitation: upload/download make KMS API calls that count toward the KMS quota (request a quota increase if throttled).
  • SSE-C — you manage your own keys; AWS doesn't store them; HTTPS required; must use the CLI/SDK.
  • Client-Side Encryption — client encrypts before upload and decrypts after download (e.g., S3 Encryption Client); you fully manage keys.

Encryption in Transit (SSL/TLS)

  • S3 exposes HTTP (unencrypted) and HTTPS (encrypted) endpoints; HTTPS recommended (required for SSE-C).
  • Force HTTPS with a bucket policy condition aws:SecureTransport: true.

Default Encryption vs Bucket Policies

  • SSE-S3 auto-applies to new objects; bucket policies (evaluated before default encryption) can reject PUTs lacking encryption headers.

CORS (Cross-Origin Resource Sharing)

  • Lets a browser fetch resources from a different origin if the target sets Access-Control-Allow-Origin.
  • Origin = scheme + host + port (e.g., https://www.example.com; implied 443 for HTTPS, 80 for HTTP).

MFA Delete

  • Requires MFA to permanently delete an object version or suspend versioning. Versioning must be enabled; only the bucket owner (root) can enable/disable it.

Access Logs

  • Log all requests to another bucket (in the same Region); analyze with Athena. Don't log to the monitored bucket (feedback loop).

Pre-Signed URLs

  • Temporary URLs that inherit the generator's permissions for GET/PUT.
  • Expiration: Console up to 12 hr; CLI up to 168 hr.
  • Use cases: time-limited downloads/uploads for logged-in or ever-changing users.

Glacier Vault Lock

  • WORM (Write Once Read Many); create and lock a vault-lock policy to prevent future edits. For compliance/retention — once written, can't be deleted.

Object Lock (requires versioning)

  • WORM at the object level.
  • Compliance mode — no one (including root) can overwrite/delete or shorten retention.
  • Governance mode — most users can't change it; some have special permissions.
  • Retention period (extendable) and Legal Hold (protected indefinitely; needs IAM permission to set/remove).

Access Points

  • Give access to whole folders/prefixes — good for granting groups the right access.
  • VPC Origin — make an access point reachable only from within a VPC (requires a VPC endpoint; the endpoint policy must allow the bucket and access point).

S3 Object Lambda

  • S3 bucket → supporting access point → Lambda → Object Lambda access point → client. Transform object data on the fly for the client.

11. CloudFront & Global Accelerator

AWS CloudFront

  • Content Delivery Network (CDN) — caches content at edge locations for lower latency and better read performance.
  • 216+ points of presence globally; DDoS protection via integration with AWS Shield and AWS WAF.

Origins

  • S3 bucket — distribute/cache files; upload through CloudFront; secured with Origin Access Control (OAC).
  • VPC Origin — apps in private subnets (ALB/NLB/EC2).
  • Custom Origin (HTTP) — S3 website endpoint or any public HTTP backend (in or out of AWS).

CloudFront vs S3 Cross-Region Replication

  • CloudFront — global edge network; files cached for a TTL; great for static content needed everywhere.
  • S3 CRR — set up per Region; near-real-time, read-only; great for dynamic content needed at low latency in a few Regions.

VPC Origins

  • Deliver content from apps in private subnets (ALB/NLB/EC2). Users → CloudFront edge → VPC origin → private subnet.
  • For public network: edge → public EC2/ALB (ALB must have a public IP, correct security groups).

Geo Restriction

  • Allow-list or block-list by country (via a 3rd-party Geo-IP DB). Use case: copyright/licensing restrictions.

Pricing & Price Classes

  • Data-out cost varies by location (e.g., India is expensive); the more you transfer, the cheaper per GB.
  • Price Class All — all Regions, best performance.
  • Price Class 200 — most Regions, excludes the most expensive.
  • Price Class 100 — least expensive Regions only (NA, EU).

Cache Invalidations

  • CloudFront doesn't know about origin updates until the TTL expires. Force a refresh with invalidations — all files (*) or a path (/test/*).

Global Users — Unicast vs Anycast

  • Unicast — one server, one IP.
  • Anycast — many servers share one IP; the client is routed to the nearest.

AWS Global Accelerator

  • Uses 2 Anycast IPs and the AWS internal network to route to the closest edge, then to your application.
  • Works with Elastic IP, EC2, ALB, NLB (public or private).
  • Consistent performance: intelligent low-latency routing, fast regional failover, no client cache issues (IP doesn't change).
  • Health checks make your app global (failover < 1 min) — great for DR.
  • Security: DDoS protection via Shield; only 2 external IPs to whitelist.

Global Accelerator vs CloudFront

  • Both use edge locations, the AWS global network, and Shield.
  • CloudFront — caches content at the edge; improves cacheable + dynamic (API acceleration, site delivery) content.
  • Global Accelerator — proxies packets at the edge to apps in one or more Regions over TCP/UDP; good for non-HTTP (gaming, IoT, VoIP) and HTTP cases needing static IPs or deterministic fast regional failover.

12. Storage Extras

AWS Snowball

  • Highly secure portable device to migrate petabytes of data offline (use it if a transfer would take > 1 week).
  • Variants for storage and for compute; for edge computing it can run EC2 instances / Lambda (preprocess data, ML, transcoding).
  • You receive it, load data, ship it back; AWS imports it.
  • Snowball → Glacier: Snowball can't import directly to Glacier — import to S3 first, then use a lifecycle policy.

Amazon FSx

Fully managed 3rd-party high-performance file systems:

  • FSx for Windows File Server — SMB + NTFS; Active Directory integration, ACLs, quotas; mountable on Linux; supports DFS Namespaces; scales to 10s of GB/s, millions of IOPS, 100s of PB; SSD (latency-sensitive) or HDD; on-prem access via VPN/Direct Connect; Multi-AZ; daily backups to S3.
  • FSx for Lustre — parallel distributed file system for HPC, ML, video, financial modeling, EDA; scales to 100s of GB/s, millions of IOPS, sub-ms latency; SSD or HDD; seamless S3 integration (read S3 as a file system, write results back); on-prem access via VPN/Direct Connect.
  • FSx for NetApp ONTAP — NFS/SMB/iSCSI; migrate ONTAP/NAS workloads; works with Linux/Windows/macOS/VMware/Workspaces/EC2/ECS/EKS; auto-grow/shrink; snapshots, replication, compression, dedup; instant point-in-time cloning.
  • FSx for OpenZFS — NFS; migrate ZFS workloads; up to 1,000,000 IOPS at 0.5 ms latency; snapshots, compression, instant cloning.

Deployment options: Scratch (temp, not replicated, high burst, cost-optimized) and Persistent (long-term, replicated within an AZ, failed files replaced in minutes).

Storage Gateway (Hybrid)

  • Bridge between on-prem and cloud (DR, backup/restore, tiered storage, on-prem cache & low-latency access). Installed on your data center / VM, or order a hardware appliance.
  • S3 File Gateway — NFS/SMB to the app server; gateway uses HTTPS to S3; caches recently used data; lifecycle to Glacier; IAM roles per gateway; SMB integrates with Active Directory.
  • FSx File Gateway — (discontinued) native access to FSx for Windows with a local cache.
  • Volume Gateway — block storage over iSCSI backed by S3; EBS snapshots; Cached volumes (recent data cached) vs Stored volumes (full dataset on-prem, scheduled S3 backups).
  • Tape Gateway — virtual tape library backed by S3/Glacier; works with existing tape-based backup software (iSCSI).

AWS Transfer Family

  • FTP/FTPS/SFTP access into/out of S3 or EFS. FTP = unencrypted; FTPS/SFTP = encrypted in flight.
  • Fully managed; pay per provisioned endpoint per hour + data transfer; manage user credentials in the service; optional Route 53; needs an IAM role to access S3/EFS.

AWS DataSync

  • Move large amounts of data:
    • On-prem / other cloud → AWS (needs an agent).
    • AWS → AWS, across storage services (no agent).
  • Targets: S3 (incl. Glacier), EFS, FSx.
  • Scheduled hourly/daily/weekly; preserves file permissions and metadata; up to 10 Gbps per agent (with bandwidth limit); use Snowcone (agent pre-installed) if network capacity is limited.

13. Decoupling — SQS, SNS, Kinesis & Amazon MQ

Integration Patterns

  • Synchronous — services talk directly. Asynchronous — middleware decouples them.
  • Decouple with SQS (queue), SNS (pub/sub), Kinesis (real-time streaming) — this layer absorbs spikes and scales.

Amazon SQS — Standard Queue

  • Fully managed queue: producers send messages; consumers poll and process.
  • Unlimited throughput and messages; retention default 4 days (max 14); latency < 10 ms; 256 KB max per message.
  • At-least-once delivery (possible duplicates); best-effort ordering (possible out-of-order).

Producing: producers send messages via SDK (e.g., order details). Consuming: consumers (EC2, on-prem, Lambda) poll up to 10 messages at a time and must delete after processing. Multiple consumers: scale horizontally; two instances can process the same message twice (at-least-once). With ASG: poll the queue, scale on queue length via CloudWatch; use SQS as a buffer for DB writes (infinitely scalable) so nothing is lost under load.

Security: in-flight (HTTPS) + at-rest (KMS) + client-side encryption; IAM policies for the API; SQS Access Policies for cross-account access and letting other services (SNS, S3) write to a queue.

Visibility Timeout: after a poll, the message is hidden (default 30 s). If processing exceeds it, another consumer can pick it up (duplicate processing). A consumer can call ChangeMessageVisibility for more time. A high timeout + a crashed consumer = the message reappears only after hours.

Long Polling: wait up to 20 s (1–20) for messages — fewer API calls, lower latency. Set at queue level or per request (WaitTimeSeconds).

SQS — FIFO Queue

  • Order guaranteed; throughput 300 msg/s (3,000 with batching).
  • Deduplication via a dedup ID (duplicates removed within a 5-minute window).
  • Message Group ID (mandatory) orders messages within a group.

Amazon SNS — Pub/Sub

  • One message → many subscribers. A producer publishes to one topic; each subscriber receives it; subscribers can filter.
  • Subscribers: Email, SMS/mobile push, SQS, HTTP(S), Lambda, Kinesis Data Firehose.
  • Publishing: Topic publish (create topic → subscribe → publish) or Direct publish (mobile apps: platform application → endpoint → publish; works with GCM, APNS, ADM).
  • Security: same as SQS (HTTPS in-flight, KMS at-rest, client-side; IAM policies; SNS Access Policies for cross-account and letting services write).

SNS + SQS Fan-Out: SNS topic → multiple SQS queues; fully decoupled, no data loss; SQS adds persistence, delayed processing, retries. The SQS access policy must allow SNS to write. Works cross-Region.

SNS FIFO — ordering + dedup, same throughput limits as SQS FIFO. SNS FIFO + SQS FIFO fan-out gives ordering + dedup downstream.

Message Filtering — JSON filter policy per subscription; no policy = receives everything.

Amazon Kinesis Data Streams

  • Collect/store streaming data in real time. Producers → stream → consumers (apps, Lambda, Firehose, Managed Service for Apache Flink).
  • Retention up to 365 days; ability to replay; data can't be deleted until it expires; up to 1 MB per record.
  • Ordering guaranteed per Partition ID; KMS at rest, HTTPS in flight. Use the KPL (producer) and KCL (consumer) libraries.

Capacity modes — a stream is a set of shards; each record has a sequence number. - Provisioned — choose shard count (1 MB/s in, 2 MB/s out per shard); scale manually; pay per shard/hour. - On-Demand — no provisioning; default 4 MB/s in (or 4,000 records/s); auto-scales on the last 30 days' peak; pay per stream/hour + data.

Amazon Data Firehose

  • Near-real-time delivery of streaming data to destinations, with optional transformation.
  • Producers: SDK, Kinesis Data Streams, IoT, CloudWatch, etc.
  • Destinations: S3, Redshift, OpenSearch, 3rd-party, HTTP endpoints. Buffers then batch-flushes.
  • Fully managed, serverless, auto-scaling, pay-per-use. Formats: CSV/JSON/Parquet/Avro/raw/binary; converts to Parquet/ORC, compresses (gzip/snappy); custom transforms via Lambda.

Amazon MQ

  • Managed message broker for RabbitMQ and ActiveMQ; protocols MQTT, AMQP, STOMP, OpenWire, WSS.
  • Doesn't scale like SQS/SNS; runs on servers (Multi-AZ with failover); has both queue and topic features. Use it when migrating apps that already use these protocols.

14. Containers — ECS, Fargate, ECR & EKS

Docker

  • A platform to package apps in containers that run the same on any OS — no compatibility issues, predictable, portable, easy to maintain. Use cases: microservices, lift-and-shift to AWS.
  • Docker vs VMs: containers share the host OS kernel (lighter, faster, near-instant); VMs run a full OS on a hypervisor (stronger isolation, more resources).
  • Images stored in: Docker Hub (public) or Amazon ECR (private + public gallery).
  • Flow: Dockerfile → image → repository → pull & run → container.

Amazon ECS

  • AWS's own container platform. Running containers = launching ECS tasks on ECS clusters.
  • EC2 Launch Type — you provision/maintain EC2 instances; each must run the ECS agent to register; AWS starts/stops containers.
  • Fargate Launch Type — serverless; no infrastructure to provision; just define task definitions; scale by increasing the task count.

IAM Roles: - EC2 Instance Profile (EC2 launch type) — used by the ECS agent: API calls to ECS, send logs to CloudWatch, pull from ECR, read Secrets Manager / SSM Parameter Store. - ECS Task Role — per-task role (one task → S3, another → DynamoDB); defined in the task definition.

Load Balancer Integration: ALB for most cases; NLB for high-throughput/performance or PrivateLink; CLB supported but not recommended.

Data Volumes (EFS): mount an EFS file system on both EC2 and Fargate tasks to share data across AZs (Fargate + EFS = serverless). S3 cannot be mounted as a file system.

Service Auto Scaling (uses Application Auto Scaling): scale on average CPU, average memory, or ALB request count per target; strategies — Target Tracking, Step Scaling, Scheduled Scaling. ECS Service Auto Scaling (task level) ≠ EC2 Auto Scaling (instance level), but they work together.

EC2 launch type scaling: use an ECS Cluster Capacity Provider (paired with an ASG) to add EC2 instances when capacity is missing — better than plain ASG scaling.

Event-driven examples: EventBridge runs an ECS task on S3 upload (process → DynamoDB); scheduled ECS tasks (hourly batch → S3); SQS queue polled by a service that auto-scales on queue depth; intercept stopped tasks via EventBridge → SNS alert.

Amazon ECR

  • Stores/manages Docker images (public or private); integrated with ECS, backed by S3.
  • EC2 instances pull via an IAM role; supports vulnerability scanning, versioning, tags, lifecycle policies.

Amazon EKS

  • Managed Kubernetes — alternative to ECS; cloud-agnostic. Use it if you already run Kubernetes elsewhere and want to migrate.
  • Worker nodes per AZ run pods (≈ ECS tasks), managed by an ASG.
  • Node types: Managed Node Groups (AWS creates/manages nodes in an EKS-managed ASG; On-Demand or Spot), Self-Managed Nodes (you create and register; prebuilt EKS-optimized AMI; On-Demand or Spot), Fargate (no nodes to manage).
  • Data volumes: specify a StorageClass + CSI driver — EBS, EFS (the only one that works with Fargate), FSx for Lustre, FSx for NetApp ONTAP.

AWS App Runner

  • Fully managed deploy of web apps/APIs at scale from source code or a container image; auto-build/deploy, auto-scaling, HA, load balancer, encryption, VPC access; connect to DB/cache/queues. Pay per vCPU and GB. Use cases: web apps, APIs, microservices, rapid deployments.

AWS App2Container (A2C)

  • CLI tool to migrate Java/.NET web apps into Docker containers (lift-and-shift from on-prem/VMs/any cloud to AWS).
  • Generates CloudFormation templates, registers images to ECR, deploys to ECS/EKS/App Runner; supports CI/CD pipelines. Discovers/analyzes apps, containerizes, produces deployment artifacts.

15. Serverless — Lambda, DynamoDB, API Gateway & More

What's Serverless

  • You don't provision or manage servers. Started with Lambda; now includes managed databases, messaging, storage.
  • Example stack: static content from S3, login via Cognito, REST API via API Gateway → Lambda → DynamoDB.

Lambda Overview

  • Virtual functions, no servers; max runtime 15 minutes; on-demand; auto-scaling; pay per request + compute time.
  • Free tier: 1M requests + 400,000 GB-seconds/month.
  • Integrates with API Gateway, Kinesis, DynamoDB (triggers), S3, CloudFront, EventBridge, CloudWatch Logs, SNS, SQS, Cognito; up to 10 GB RAM; monitor via CloudWatch.
  • Container images supported (must implement the Lambda Runtime API); for arbitrary Docker images, prefer ECS/Fargate.
  • Examples: generate thumbnails on S3 upload; serverless CRON via an EventBridge rule.

Limits (per Region)

  • Memory 128 MB–10 GB (1 MB steps); max runtime 900 s; env vars 4 KB; /tmp 512 MB–10 GB; default concurrency 1,000 (increasable via support).
  • Deployment: 50 MB (zipped), 250 MB (unzipped code + deps); load extra files into /tmp at startup.

Concurrency & Throttling

  • Limit concurrent executions; over the limit → throttle. Synchronous → ThrottleError 429; asynchronous → retries then DLQ.
  • If one function uses all 1,000 concurrent executions, other functions get throttled (set reserved concurrency).
  • Async invocations retry for up to 6 hours (1 s → 5 min backoff).

Cold Starts & Provisioned Concurrency

  • Cold start — first request to a new instance runs init code (higher latency); large dependencies = slower init.
  • Provisioned Concurrency — allocate ahead of time for low latency (manage with Application Auto Scaling).
  • VPC cold starts have been dramatically reduced.

Lambda SnapStart

  • Free performance boost for Java, Python, .NET — pre-initializes the function (memory + disk state saved on publish) for low-latency starts.

Edge Functions

Run logic at the edge before reaching the app — attached to a CloudFront distribution; serverless, pay-per-use.

  • CloudFront Functions — lightweight JavaScript; sub-ms startup, millions of req/s; change viewer request/response only; native to CloudFront. Use: cache-key normalization, header manipulation, URL rewrites/redirects, request auth.
  • Lambda@Edge — Node.js/Python; thousands of req/s; change viewer and origin request/response; author in one Region, CloudFront replicates. Use: longer execution, adjustable CPU/memory, network access, file-system/HTTP-body access.
  • CloudFront Functions are much faster; Lambda@Edge does more.

Lambda Networking

  • By default, Lambda runs outside your VPC (can't reach RDS/ElastiCache/internal ELB). Launch it in a VPC by setting VPC ID, subnets, and security groups (Lambda creates an ENI).
  • With RDS Proxy — pool connections (Lambda can open too many); improves availability (−66% failover) and security (IAM auth, Secrets Manager). Lambda must be in a VPC (the proxy isn't public).
  • Invoking Lambda from RDS/Aurora — process data events from within the DB (RDS PostgreSQL, Aurora MySQL); allow outbound traffic and grant invoke permissions.
  • RDS Event Notifications — info about the DB itself (not the data); near-real-time → SNS/EventBridge → Lambda.

Amazon DynamoDB

  • Fully managed NoSQL, HA with replication across AZs; massive scale (millions of req/s, trillions of rows, 100s of TB); single-digit ms latency; IAM-integrated; auto-scaling; no maintenance. Standard and IA table classes.
  • Basics: tables have a primary key; infinite items; attributes (can be null, evolve over time); max item size 400 KB. Types: scalar (string, number, bool, null, binary), document (list, map), set.

Capacity modes: - Provisioned (default) — set RCUs/WCUs, plan capacity, optional auto-scaling. - On-Demand — auto-scales, no planning; great for unpredictable/spiky workloads.

DAX (DynamoDB Accelerator) — in-memory cache for DynamoDB; default 5-min TTL; no app changes; for individual-object and Query/Scan caching (ElastiCache is better for big aggregations).

Stream Processing: react to table changes. - DynamoDB Streams — 24-hr retention, limited consumers; process via Lambda triggers or the Kinesis adapter. - Kinesis Data Streams (newer) — 1-year retention, many consumers; process via Lambda, Kinesis Data Analytics, Firehose, Glue.

Global Tables — multi-Region, low latency; requires DynamoDB Streams. TTL — auto-delete items after a timestamp (e.g., web sessions). Backups for DR: continuous PITR (last 35 days, restores to a new table) and on-demand backups (long-term, managed via AWS Backup, restores to a new table). With S3: export to S3 (no read-capacity impact) for Athena analysis / auditing / ETL; import from S3 (creates a new table; errors logged to CloudWatch).

API Gateway

  • Lambda + API Gateway = no infrastructure. Supports WebSocket, API versioning, environments, security (authn/authz), API keys, throttling, Swagger/OpenAPI import, request/response transform & validation, SDK generation, response caching. Works with Lambda, HTTP, AWS services.

Endpoint types: - Edge-Optimized (default) — global clients; requests via CloudFront edge; the API still lives in one Region. - Regional — same-Region clients; optionally combine with CloudFront manually. - Private — accessible only from your VPC via an interface VPC endpoint (ENI); use a resource policy.

Security: authentication via IAM roles (internal), Cognito (external/mobile), or custom authorizers. Custom domain HTTPS via ACM (Edge-Optimized cert must be in us-east-1; Regional cert in the API's Region); set up a CNAME or A-Alias in Route 53.

AWS Step Functions

  • Serverless visual workflow orchestrating Lambda (and EC2, ECS, on-prem, API Gateway, SQS). Features: sequence, parallel, conditions, timeouts, error handling, human approval. Use cases: order fulfillment, data processing, any workflow.

Amazon Cognito

  • User Pools — sign-in for app users; integrates with API Gateway & ALB; serverless user directory; email/password login, password reset, email/phone verification, MFA.
  • Identity Pools — give users temporary AWS credentials to access AWS resources directly; integrate with User Pools, AWS services, API Gateway, or 3rd-party login.
  • Cognito is for large numbers of (often mobile) users and SAML auth, vs IAM.

16. Serverless Patterns

Microservices

  • Switch to microservices that talk via REST APIs; each can have its own architecture for leaner development.
  • Synchronous patterns: API Gateway, load balancers. Asynchronous: SQS, Kinesis, SNS, Lambda triggers.
  • Challenges (per-service overhead, server density, multiple versions, client-side integration) are eased by serverless: clone APIs, reproduce environments, auto-scaling, pay-per-use, generated SDKs.

Software Updates Offloading

  • An EC2 app distributes updates; bursts of traffic when an update drops; don't change the app.
  • Design: front with CloudFront to cache update files at the edge — serverless and auto-scaling.

17. Choosing the Right Database

  • RDS — managed relational (PostgreSQL/MySQL/Oracle/SQL Server/DB2/MariaDB/Custom); read replicas + Multi-AZ; provisioned instance + EBS; IAM/SG/KMS/SSL; auto backups (PITR up to 35 days) + manual snapshots; IAM auth + Secrets Manager. Use: OLTP, SQL queries, transactions.
  • Aurora — PostgreSQL/MySQL-compatible; storage and compute separate; storage Multi-AZ (6 copies / 3 AZs); HA, self-healing, auto-scaling; serverless option; Global (16 read instances per Region); Aurora ML; fast cloning. Use: like RDS but less maintenance, more performance/features.
  • ElastiCache — managed Redis/Memcached; in-memory, sub-ms; clustering + Multi-AZ + read replicas (Redis); IAM/SG/KMS/Redis Auth; backup/PITR; needs app code changes. Use: key/value, frequent reads, session data, cache DB queries (no SQL).
  • DynamoDB — managed NoSQL, ms latency; provisioned/on-demand; can replace ElastiCache as a key/value store (with TTL); HA, Multi-AZ by default; DAX read cache; IAM; flexible schema. Use: serverless apps (small docs), distributed serverless cache.
  • S3 — key/value object store; great for big objects; serverless, infinite scale, max object 5 TB; versioning; tiers + lifecycle; IAM/bucket policies/ACL/Access Points/Object Lambda/CORS/Object Lock; SSE-S3/KMS/C + client-side; batch ops, inventory; multipart, Transfer Acceleration, S3 Select. Use: static files, big-file key/value store, website hosting.
  • DocumentDB — Aurora-style MongoDB; NoSQL JSON; HA across 3 AZs; storage grows in 10 GB increments; auto-scales to millions of req/s.
  • Neptune — managed graph DB; HA across 3 AZs, up to 15 read replicas; billions of relationships, ms queries. Use: knowledge graphs, fraud detection, recommendations, social networks. Neptune Streams — real-time ordered change log, no dups, accessible via REST.
  • Keyspaces — managed Apache Cassandra; serverless, scalable, HA; auto-scales tables; replicated 3× across AZs; CQL; on-demand/provisioned; encryption, backup, PITR (35 days). Use: IoT device info, time-series.
  • QLDB — Quantum Ledger Database; for financial transactions; serverless, HA across 3 AZs; immutable, cryptographically verifiable; SQL-like; centralized (Amazon-owned, no decentralization).
  • Timestream — managed serverless time-series DB; auto-scales; trillions of events; faster and cheaper than relational; encryption in transit and at rest.

Amazon MSK (Managed Streaming for Apache Kafka)

20. Monitoring & Audit — CloudWatch, CloudTrail & Config

CloudWatch Metrics

  • Data about system performance; metrics belong to namespaces; dimensions are attributes (up to 30 per metric); metrics have timestamps.
  • Build dashboards; create custom metrics (e.g., RAM).
  • Metric Streams — near-real-time, low-latency delivery to Firehose (→ destinations) or 3rd parties; optionally filter a subset.

CloudWatch Logs

  • Store application logs. Log groups (define first) contain log streams (instances/files/containers); set expiration policies.
  • Can send logs to: S3 (export), Kinesis Data Firehose, Kinesis Data Streams, Lambda, OpenSearch.
  • Encrypted by default; optional KMS with your own keys.
  • Sources: SDK, CloudWatch Logs Agent, Unified Agent, Elastic Beanstalk, ECS, Lambda, VPC Flow Logs, API Gateway, CloudTrail (filtered), Route 53 (DNS queries).
  • Logs Insights — query/analyze logs with a purpose-built language; auto-discovers fields; aggregate/sort/filter; save queries; query across log groups and accounts. It's a query engine, not real-time.
  • S3 Export — up to 12 hr (CreateExportTask); not near-real-time.
  • Subscriptions — real-time log data to Kinesis Data Streams, Firehose, or Lambda; subscription filters; cross-account (recipient needs a destination access policy; an IAM role for KDS).
  • Live Tail — view events as they post (great for debugging; ~1 hr free/day).
  • For EC2 — install the agent (default: no logs go to CloudWatch); the instance needs an IAM role; works on your own servers too.

Agents

  • Logs Agent (old) — sends only to CloudWatch Logs.
  • Unified Agent — collects system-level metrics (CPU, disk, RAM, netstat, processes, swap — beyond the default CPU/disk/network) and logs; centralized config via SSM Parameter Store.

Alarms

  • Trigger notifications from a metric; states: OK, INSUFFICIENT_DATA, ALARM.
  • Period = evaluation length in seconds (high-resolution custom metrics: 10/30 s or multiples of 60).
  • Targets: stop/terminate/reboot/recover an EC2 instance; trigger an Auto Scaling action; notify SNS.
  • Composite Alarms — monitor the states of multiple alarms with AND/OR; reduce alarm noise.
  • EC2 instance recovery — status checks: instance (the VM), system (underlying hardware), attached EBS. On recovery you keep the same private/public/Elastic IP, metadata, and placement group.
  • Alarms can be based on Logs Metric Filters; test via the CLI by setting the alarm state.

Amazon EventBridge

  • Schedule jobs (CRON) and react to event patterns (e.g., root login → Lambda); trigger Lambda, send SQS/SNS; archive and replay events.
  • Sources: EC2, CodeBuild, S3, Trusted Advisor, CloudTrail, schedule/CRON. Destinations: Lambda, Batch, ECS, SQS, SNS, Kinesis, Step Functions, CodePipeline/CodeBuild, SSM, EC2 actions.
  • Schema Registry — infer event schemas, generate code, version schemas.
  • Resource-based Policy — manage permissions per event bus (e.g., aggregate org-wide events into one account/Region).

CloudWatch Insights (Operational Visibility)

  • Container Insights — metrics + logs from ECS, EKS, Kubernetes on EC2, Fargate (needs an agent for Kubernetes).
  • Lambda Insights — detailed metrics to troubleshoot serverless (CPU, memory, cold starts); provided as a Lambda Layer.
  • Contributor Insights — top-N contributors from logs (find bad hosts, heavy network users, error-heavy URLs); works on any AWS-generated logs.
  • Application Insights — automated dashboards for app problems (EC2 with select tech: Java, .NET, IIS, databases); powered by SageMaker; findings to EventBridge + SSM OpsCenter.

AWS CloudTrail

  • Governance, compliance, and audit; on by default; records API calls/events (Console, SDK, CLI, AWS services).
  • Send logs to CloudWatch Logs or S3; a trail can be all-Regions (default) or single-Region.
  • If a resource is deleted, check CloudTrail first.
  • Event types:
    • Management Events — operations on resources; logged by default; separable read/write.
    • Data Events — high-volume; not logged by default; S3 object-level activity, Lambda execution.
    • Insights Events — must be enabled (paid); detect unusual activity (inaccurate provisioning, hitting service limits, IAM bursts, maintenance gaps) by baselining normal management events and analyzing write events.
  • Retention: 90 days by default; send to S3 + Athena for longer.

EventBridge + CloudTrail — all API calls can become EventBridge events (e.g., DeleteTable → CloudTrail → EventBridge → SNS alert; or AssumeRole).

AWS Config

  • Audit and record compliance/configuration of resources over time; answers "Is SSH unrestricted?", "Are buckets public?", "How did my ALB config change?".
  • SNS alerts on changes; per-Region service (aggregatable across Regions/accounts); store data in S3 (analyze with Athena).
  • Rules — AWS-managed or custom (via Lambda); evaluated on each change and/or at intervals. Config records and tracks but doesn't prevent. Not free.
  • Resource view — compliance, configuration, and CloudTrail API calls over time.
  • Remediations — SSM Automation Documents auto-fix non-compliant resources (e.g., deactivate an expired IAM access key); can invoke Lambda; set retries.
  • Notifications — via EventBridge or SNS.

21. IAM Advanced

AWS Organizations

  • Global service to manage multiple accounts: one management account + member accounts (a member belongs to only one org).
  • Consolidated billing; shared RI/Savings Plans discounts; API to automate account creation.
  • Organizational Units (OUs) — Root OU contains the management account; create sub-OUs (Dev, HR, etc.).
  • Advantages: multi-account vs one-account-multi-VPC, CloudTrail on all accounts, central CloudWatch Logs account, cross-account admin roles.
  • Service Control Policies (SCPs) — IAM policies on OUs/accounts to restrict users and roles; don't apply to the management account; need an explicit allow from the root through each OU to the target account.

IAM Conditions

  • Allow/deny actions and resources based on conditions.

IAM Roles vs Resource-Based Policies

  • Cross-account access: attach a resource-based policy to a resource, or use a role as a proxy.
  • When assuming a role, you give up your own permissions; with a resource-based policy, you keep them.

EventBridge Security

  • A rule needs permission on its target: Lambda, SNS, SQS, S3, API Gateway use resource-based policies; Kinesis streams, EC2 Auto Scaling, SSM Run Command use an IAM role.

IAM Permission Boundaries

  • Define the maximum permissions an IAM user/role can have (supported for users and roles, not groups); combine with SCPs. Use: delegate user creation to non-admins within bounds.

IAM Identity Center

  • One login for all accounts in an Organization; also business cloud apps and SAML 2.0 apps; SSO for AWS Organizations, Windows EC2 instances, and custom apps.
  • Identity store: built-in or 3rd-party.
  • Use Permission Sets (collections of IAM policies) associated with OUs and assigned to groups.
  • Fine-grained permissions: multi-account (permission sets), application assignments (SAML 2.0 apps with URLs/certs/metadata), and ABAC (attribute-based access control — permissions from user attributes like cost center, title, locale).

Microsoft Active Directory & Directory Service

  • AD — database of objects (users, computers, printers, shares, security groups) on Windows Server with AD Domain Services; centralized security.
  • Directory Service options:
    • AWS Managed Microsoft AD — your own AD in AWS, manage users locally, MFA; establish trust with on-prem AD.
    • AD Connector — proxy to on-prem AD (users managed on-prem); MFA.
    • Simple AD — AD-compatible managed directory; can't join on-prem AD (use when you have none).
  • Identity Center + AD setup: connect to AWS Managed Microsoft AD (out-of-the-box) or a self-managed directory (two-way trust with AWS Managed Microsoft AD, or use AD Connector).

AWS Control Tower

  • Easily set up and govern a secure, compliant multi-account environment; uses Organizations to create accounts.
  • Automates environment setup and policy management; detects and remediates violations; dashboard for compliance.
  • Guardrails: Preventive (via SCPs) and Detective (via AWS Config).

22. Security & Encryption — KMS, Shield, WAF

Encryption Basics

  • In flight (TLS/SSL) — encrypt before sending, decrypt on receipt; stops man-in-the-middle.
  • Server-side at rest — server encrypts after receiving and decrypts before sending; needs access to the key.
  • Client-side — client encrypts/decrypts; server never sees plaintext; can use envelope encryption.

AWS KMS

  • AWS manages encryption keys; integrated with IAM (authorization) and CloudTrail (audit); built into most services. Never store secrets in plaintext.
  • Key types by algorithm:
    • Symmetric (AES-256) — one key encrypts and decrypts; used by AWS services; never exposed unencrypted (use the KMS API).
    • Asymmetric (RSA & ECC) — public (encrypt) / private (decrypt) pair; for encrypt/decrypt or sign/verify; public key downloadable, private key not; use for encryption outside AWS by users who can't call the KMS API.
  • Key categories: AWS Owned (free — SSE-S3, SSE-SQS, SSE-DDB), AWS Managed (free — aws/service-name), Customer-Managed created ($1/mo), Customer-Managed imported ($1/mo); plus $0.03 per 10,000 API calls.
  • Rotation: AWS-Managed → automatic yearly; Customer-Managed → enable for automatic + on-demand; Imported → manual only (needs an alias).

Copying snapshots across Regions: KMS keys are Region-scoped — snapshot the encrypted EBS volume, copy to the new Region re-encrypting with a different KMS key; the restored snapshot uses that key.

Key Policies: control access to keys (like S3 bucket policies, but you can't control access without them). - Default — full access to the root user (entire account). - Custom — define users/roles, who can administer; useful for cross-account access (good for sharing encrypted snapshots).

Multi-Region Keys — a primary key replicated to other Regions with the same key ID, key material, and rotation; encrypt in one Region, decrypt in another, no cross-Region API calls. Not global — each replica is managed independently. Use: global client-side encryption, Global DynamoDB / Aurora.

Client-Side Encryption + Global Tables/Aurora — encrypt specific attributes (e.g., SSNs) client-side (DynamoDB Encryption Client / AWS Encryption SDK); with a multi-Region key replicated alongside the global table, clients decrypt locally with low-latency KMS calls — protecting fields even from DB admins.

S3 Replication encryption: unencrypted and SSE-S3 objects replicate by default; SSE-C can replicate; for SSE-KMS you must enable the option (specify the target KMS key, adapt the target key policy, grant an IAM role kms:Decrypt on source + kms:Encrypt on target; watch for KMS throttling). Multi-Region keys are treated as independent by S3.

AMI sharing (encrypted via KMS): modify the image launch permission for the target account; share the KMS key used to encrypt the snapshot; the target IAM role/user needs DescribeKey, ReEncrypt*, CreateGrant, Decrypt; the target can optionally re-encrypt volumes with its own key on launch.

SSM Parameter Store

  • Secure storage for configs and secrets; optional KMS encryption; serverless, scalable, durable; version tracking; IAM security; EventBridge notifications; CloudFormation integration; hierarchical (folder-like) structure.
  • Parameter Policies (advanced) — assign TTL/expiration, multiple policies (e.g., delete at a time + notify 15 days before + notify after 20 days of no change).

AWS Secrets Manager

  • For secrets; force rotation every X days (Parameter Store can't); automatic secret generation on rotation (Lambda); integrates with RDS (MySQL/PostgreSQL/Aurora); encrypted with KMS; mostly for RDS.
  • Multi-Region Secrets — replicate across Regions, keep read replicas in sync, promote a replica to standalone. Use: multi-Region apps, DR.

AWS Certificate Manager (ACM)

  • Provision/manage/deploy TLS certs (HTTPS in-flight encryption); public and private certs; free for public certs; automatic renewal.
  • Integrates with ELB (ALB/NLB/CLB), CloudFront, API Gateway. Can't be used with EC2 instances directly.
  • Public certs: list domains (FQDN or wildcard), choose validation (DNS preferred for automation, via a CNAME; or email to WHOIS contacts); wait a few hours; auto-renews.
  • Imported certs: no auto-renewal; ACM sends daily expiration events starting 45 days out (configurable) to EventBridge; AWS Config rule acm-certificate-expiration-check flags expiring certs.
  • ALB integration: redirect HTTP → HTTPS.
  • API Gateway: create a custom domain; Edge-Optimized cert must be in us-east-1, Regional cert in the API's Region; set a CNAME or A-Alias in Route 53.

AWS WAF (Web Application Firewall)

  • Protects against common web exploits at Layer 7 (HTTP). Deploy on ALB, API Gateway, CloudFront, AppSync GraphQL, Cognito User Pools.
  • Web ACL rules: IP Sets (up to 10,000 IPs per set), HTTP header/body/URI inspection (SQL injection, XSS), size constraints, geo-match (block countries), rate-based rules (DDoS).
  • Web ACLs are regional (except for CloudFront). A rule group is a reusable set of rules.
  • Fixed IP with WAF + LB: WAF can't attach to an NLB (Layer 4) — use Global Accelerator for a fixed IP, then WAF on the ALB.

AWS Shield (DDoS)

  • Standard — free; protects against SYN/UDP floods, reflection, and other L3/L4 attacks.
  • Advanced — paid; protects EC2, ELB, CloudFront, Global Accelerator, Route 53; 24/7 DDoS Response Team; cost protection during DDoS spikes; automatic application-layer (L7) DDoS mitigation that auto-creates WAF rules.

AWS Firewall Manager

  • Manage rules across all accounts in an Organization via security policies (WAF rules, Shield Advanced, security groups, Network Firewall, Route 53 Resolver DNS Firewall). Policies are Region-level; applied to current and future resources.

DDoS Protection Best Practices

  • CloudFront — edge delivery + common DDoS protection.
  • Global Accelerator — edge access + Shield integration (when the backend isn't CloudFront-compatible).
  • Route 53 — DNS at the edge + DDoS protection.
  • EC2 + Auto Scaling — absorb traffic; ELB spreads load.
  • CloudFront + WAF — cache static content, block by request signature; WAF rate-based rules auto-block bad IPs; managed rules block by IP reputation; CloudFront geo-blocking.
  • Shield Advanced — auto L7 mitigation via WAF rules.
  • Obfuscate resources — CloudFront/API Gateway/ELB hide backend (Lambda, EC2).

Amazon GuardDuty

  • Intelligent threat detection using ML, anomaly detection, and 3rd-party data; one-click enable.
  • Inputs: CloudTrail (management + S3 data events), VPC Flow Logs, DNS logs, optional features.
  • EventBridge rules → Lambda/SNS on findings; dedicated findings for cryptocurrency attacks.

Amazon Inspector

  • Automated security assessments for EC2 (network accessibility + OS CVEs), ECR container images (on push), and Lambda (code + dependency vulnerabilities, on deploy).
  • Continuous scanning; CVE database; network reachability (EC2); risk scores for prioritization; findings to EventBridge + Security Hub.

Amazon Macie

  • Managed data security/privacy using ML + pattern matching to discover and protect sensitive data (PII) in S3; alerts via EventBridge.

23. Networking — VPC

VPC = Virtual Private Cloud.

CIDR — IPv4

  • Classless Inter-Domain Routing — defines an IP range. Examples: /32 = one IP; 0.0.0.0/0 = all IPs; 192.168.0.0/26 = 64 addresses.
  • Two parts: Base IP (e.g., 10.0.0.0) and Subnet Mask (how many bits can change).
  • Mask sizes: /8 = 255.0.0.0, /16 = 255.255.0.0, /24 = 255.255.255.0, /32 = 255.255.255.255.
  • IPs have 4 octets: /32 = none change, /24 = last octet, /16 = last 2, /8 = last 3, /0 = all.
  • Address counts: /32 = 1, /31 = 2, /24 = 256, /16 = 65,536.

Public vs Private IP (IANA ranges)

  • Private only: 10.0.0.0/8 (big networks), 172.16.0.0/12 (AWS default VPC range), 192.168.0.0/16 (home). Everything else is public.

Default VPC

  • Every account has one; new instances launch into it if no subnet is specified; it has internet connectivity and instances get public IPv4 + public/private DNS names.

VPC (IPv4)

  • Soft limit 5 VPCs per Region; max 5 CIDRs per VPC. Per CIDR: min /28 (16 IPs), max /16 (65,536 IPs). Only private ranges allowed; don't overlap with other networks.

Subnets (IPv4)

  • A sub-range of the VPC's IPs, tied to an AZ. AWS reserves 5 IPs per subnet (first 4 + last 1):
    • 1st = network address; 2nd = VPC router; 3rd = Amazon DNS; 4th = future use; 5th = broadcast.

Internet Gateway (IGW)

  • Lets VPC resources reach the internet; scales horizontally, HA, redundant; created separately from the VPC; one VPC to one IGW. An IGW alone isn't enough — route tables must be edited.

Bastion Host

  • An EC2 instance in a public subnet used to SSH into instances in private subnets.
  • Bastion security group: allow port 22 from your corporate CIDR (restrict the range). Private instances' security groups: allow the bastion's security group or private IP.

NAT Instance (legacy, may appear on exam)

  • Lets private-subnet instances reach the internet; launched in a public subnet; disable source/destination check; needs an Elastic IP; route tables route private traffic to it; not HA; you manage security groups.

NAT Gateway

  • AWS-managed NAT — higher bandwidth, HA, no admin; pay per hour + bandwidth; created in a specific AZ with an Elastic IP; can't be used by instances in the same subnet; requires an IGW (private → NATGW → IGW); 5 Gbps auto-scaling to 100 Gbps; no security groups.

Security Groups & NACLs

  • Inbound request → NACL inbound → security group inbound → instance → out via security group → NACL outbound.
  • NACL (subnet level): stateless firewall; one per subnet; numbered rules (lower number = higher precedence, 1–32766); first match wins; last rule * denies; new custom NACLs deny everything. Great for blocking a specific IP at the subnet level.
  • Default NACL — allows all inbound/outbound; don't modify it — create a custom one.
  • Ephemeral Ports — the client opens a temporary port (range varies by OS) for the server's reply; NACLs must allow outbound + inbound on 1024–65535.
  • Security Group — stateful, at the instance level.

VPC Peering

  • Privately connect two VPCs so they behave as one network; CIDRs must not overlap; not transitive (peer each pair); update route tables in each subnet.
  • Works cross-account and cross-Region; you can reference a security group in a peered VPC (same Region).

VPC Endpoints (AWS PrivateLink)

  • Connect to AWS services over the private network instead of the public internet; redundant, horizontally scalable; remove the need for IGW/NATGW. Troubleshoot via DNS resolution + route tables.
  • Interface Endpoints (PrivateLink) — provision an ENI (private IP) with a security group; support most services; $/hour + $/GB.
  • Gateway Endpoints — a route-table target (no security group); support only S3 and DynamoDB; free.
  • For access from on-prem, another VPC, or another Region — use an Interface Endpoint.

VPC Flow Logs

  • Capture IP traffic at the VPC, subnet, or ENI level (ACCEPT and REJECT); to S3, CloudWatch Logs, or Firehose; covers managed interfaces (ELB, RDS, ElastiCache, Redshift, WorkSpaces, NATGW, Transit Gateway); query with Athena or Logs Insights to find attacks.

Site-to-Site VPN

  • Connect your data center to AWS over the (encrypted) public internet.
  • Virtual Private Gateway (VGW) — AWS side; created and attached to the VPC.
  • Customer Gateway (CGW) — your side (software/hardware); needs a public routable IP (or, behind NAT, enable NAT-T and use the NAT's public IP).
  • Enable Route Propagation for the VGW in the subnet's route table; to ping instances from on-prem, allow ICMP inbound on the security group.

AWS VPN CloudHub

  • Hub-and-spoke model connecting multiple sites to one VGW so the sites can communicate; over the public internet; low-cost primary/secondary connectivity (use dynamic routing + route tables).

Direct Connect (DX)

  • Dedicated private connection from your data center to your VPC via a DX location; set up a VGW; access public (S3) and private (EC2) resources on the same connection; supports IPv4/IPv6.
  • Use cases: high/consistent bandwidth, large datasets, real-time feeds, hybrid. Public virtual interface for S3/Glacier; private for EC2.
  • DX Gateway — connect to multiple VPCs in different Regions (same account).
  • Connection types: Dedicated (1/10/100 Gbps, physical port, requested via AWS); Hosted (50 Mbps–10 Gbps, via DX Partners, capacity on demand). Lead times often > 1 month.
  • Encryption: DX is private but not encrypted — add a VPN over DX for IPsec encryption.
  • Resiliency: High = 2 DX locations; Maximum = 2 locations × 2 connections each (4 total).
  • Backup: if DX fails, use a backup DX or a Site-to-Site VPN (over the public internet).

Transit Gateway

  • Hub-and-spoke transitive peering for thousands of VPCs and on-prem (DX Gateway + CGW/VPN); regional, works cross-Region; share cross-account via RAM; route tables limit which VPCs talk; supports IP multicast.
  • ECMP (equal-cost multi-path) — forward packets over multiple best paths; create multiple Site-to-Site VPNs to increase bandwidth (1 VPN to VGW = 2 tunnels; VPN to Transit Gateway with ECMP = more tunnels/bandwidth at a cost).

Traffic Mirroring

  • Capture and inspect VPC network traffic non-intrusively; route to your security appliances. Source = ENIs; target = ENI or NLB; all or some packets; same VPC or peered VPC. Use: content inspection, threat monitoring, troubleshooting.

IPv6

  • ~3.4 × 10³⁸ addresses; every IPv6 in AWS is public/internet-routable (no private range); format is 8 groups of 4 hex digits.
  • In VPC: IPv4 can't be disabled; IPv6 runs in dual-stack; instances get a private IPv4 + public IPv6, reachable via the IGW.
  • Troubleshooting: can't launch an instance? You may be out of IPv4 addresses — add a new IPv4 CIDR to the subnet.

Egress-Only Internet Gateway

  • IPv6 equivalent of a NAT Gateway — outbound IPv6 from your VPC while blocking inbound IPv6; update route tables.

Networking Cost (per GB)

  • Use private IPs where possible (cheaper, better performance). Same Region, different AZ → use private IP. Same AZ = max savings (but lose HA).
  • Egress (outbound) traffic costs money; ingress (inbound) is typically free; keep traffic within AWS. DX co-located in the same Region = lower egress cost.

S3 Data Transfer Pricing (USA, illustrative)

  • S3 ingress: free; S3 → internet: $0.09/GB; S3 → CloudFront: free; CloudFront → internet: $0.085/GB; S3 Cross-Region Replication: $0.02/GB. Transfer Acceleration costs extra on top of transfer.
  • NAT Gateway vs Gateway VPC Endpoint — send S3 traffic via a (free) Gateway Endpoint instead of a NAT Gateway.

Network Protection

  • NACLs, security groups, WAF (malicious requests), Shield / Shield Advanced, Firewall Manager (manage across accounts).

AWS Network Firewall

  • Protect a whole VPC at Layer 3–7; inspect all traffic (VPC-to-VPC, in/out from internet, to/from DX & Site-to-Site VPN); internally uses Gateway Load Balancer; rules managed centrally cross-account.
  • Fine-grained controls (100s of rules): filter by IP/port/protocol/domain, regex pattern matching; actions allow/drop/alert; active flow inspection (intrusion prevention); send logs to S3, CloudWatch Logs, Firehose.

24. Disaster Recovery & Migrations

DR Overview

  • Types: on-prem→on-prem (traditional, expensive), on-prem→AWS (hybrid), Region A→Region B.
  • RPO (Recovery Point Objective) — how much data you can lose. RTO (Recovery Time Objective) — how much downtime.

DR Strategies (cheapest/slowest → most expensive/fastest)

  • Backup & Restore — high RPO, worst RTO, cheap (just storage cost).
  • Pilot Light — critical core always running small in the cloud; faster than backup & restore.
  • Warm Standby — full system running at minimum size; scale up to production on disaster.
  • Hot Site / Multi-Site — full production scale running active-active; very low RTO; most expensive (best RTO with Multi-Site).

DMS — Database Migration Service

  • Quickly and securely migrate databases; source stays available during migration; resilient, self-healing.
  • Homogeneous (Oracle→Oracle) and heterogeneous (SQL Server→Aurora) migrations; Continuous Data Replication (CDC); you create an EC2 instance to run the replication tasks.
  • Sources: on-prem/EC2 DBs, Azure SQL, RDS (incl. Aurora), S3, DocumentDB. Targets: on-prem/EC2 DBs, RDS, Redshift, DynamoDB, S3, OpenSearch, Kinesis, Kafka, DocumentDB, Neptune, Redis, Babelfish.
  • Multi-AZ — synchronous standby in another AZ (data redundancy, no I/O freezes, fewer latency spikes).

AWS Schema Conversion Tool (SCT)

  • Convert a schema from one engine to another (not needed for same-engine migrations).
  • Continuous replication: use SCT to convert the schema, then a DMS replication instance in your VPC moves data from the source DB into AWS.

RDS & Aurora Migrations

  • RDS MySQL → Aurora MySQL: restore an RDS snapshot as Aurora; or create an Aurora Read Replica, then promote it when lag = 0.
  • External MySQL → Aurora MySQL: Percona XtraBackup → S3 → create Aurora from S3; or mysqldump into Aurora (slower).
  • RDS PostgreSQL → Aurora PostgreSQL: restore a snapshot; or Aurora Read Replica → promote when lag = 0.
  • External PostgreSQL → Aurora PostgreSQL: backup → S3 → import via the aws_s3 extension.
  • Use DMS if both databases are up and running.

On-Premise Strategy

  • Download the Amazon Linux 2 AMI as a VM for on-prem use.
  • VM Import/Export — migrate apps to EC2, DR repository for on-prem VMs, export back to on-prem.
  • Application Discovery Service — gather server info (utilization, dependency mapping) to plan a migration; track in Migration Hub.
  • DMS — replicate on-prem↔AWS↔on-prem across DB technologies.
  • Server Migration Service (SMS) — incremental replication of live on-prem servers.

AWS Backup

  • Managed, automated backups across services: all DB engines, S3, EC2/EBS, EFS/FSx, Storage Gateway; cross-Region and cross-account; PITR (supported services); on-demand and scheduled; tag-based policies.
  • Backup Plans — frequency, window, transition to cold storage, retention; auto-stored in S3.
  • Backup Vault Lock — enforce WORM; protect against deletes and shortened retention; even root can't delete enabled backups.

Application Discovery Service

  • Plan migrations by scanning servers for utilization + dependency mapping. Agentless (VM inventory/config/performance) vs Agent-based (system config/performance, processes, network connections); data in Migration Hub.

Application Migration Service (MGN)

  • Lift-and-shift (rehost) to AWS; converts physical/virtual/cloud servers to run natively on AWS; wide platform/OS/DB support; minimal downtime and reduced cost.

Transferring Large Data

  • 200 TB over 100 Mbps internet/VPN ≈ 185 days; over 1 Gbps Direct Connect ≈ 18.5 days (≈1-month setup); Snowball ≈ 1 week to order (can combine with DMS). For ongoing transfers: Site-to-Site VPN or DX with DMS/DataSync.

VMware Cloud on AWS

  • Extend an on-prem VMware data center to AWS while keeping VMware software. Use cases: migrate vSphere workloads, run across private/public/hybrid, DR.

25. More Solution Architectures

S3 Event Notifications

  • React to object created/removed; filter by name; create as many events as needed. With EventBridge, all events flow there for advanced filtering and 18+ destinations.

Caching Strategies

  • CloudFront — cache at the edge (fast; use TTL for freshness).
  • API Gateway — regional caching.
  • App logic — Redis/Memcached/DAX. Databases and S3 don't cache.

High Performance Computing (HPC)

The cloud is ideal — spin up many resources fast, pay for what you use.

  • Data management/transfer: Direct Connect, Snowball/Snowmobile, DataSync.
  • Compute & networking: EC2 (CPU/GPU optimized, Spot + auto-scaling), cluster placement groups (low latency), Enhanced Networking (SR-IOV) — Elastic Network Adapter (ENA, up to 100 Gbps) or legacy Intel 82599VF; Elastic Fabric Adapter (EFA) — Linux only, great for tightly-coupled workloads (MPI), bypasses the OS for low-latency transport.
  • Storage: instance-attached (EBS up to 256,000 IOPS with io2 Block Express; Instance Store — low latency, millions of IOPS) and network (S3, EFS, FSx for Lustre — HPC-optimized, S3-backed).
  • Automation/orchestration: AWS Batch (multi-node parallel jobs, schedules + launches EC2) and AWS ParallelCluster (open-source HPC cluster management via text config; can enable EFA).

26. Other Services

CloudFormation

  • Infrastructure as code via templates — deploy in the right order with exact config.
  • Benefits: no manual creation, code review, cost tagging/estimation/savings, on-the-fly resource creation, automatic dependency ordering, broad resource support (custom resources for the rest).
  • Infrastructure Composer — visualize templates.
  • Service Role — an IAM role that lets CloudFormation create/update/delete resources on your behalf (users need iam:PassRole); supports least privilege (a user without direct service access can still deploy via the template).

Amazon SES (Simple Email Service)

  • Send email securely, globally, at scale; inbound and outbound; supports DKIM and SPF; flexible IP deployment; send via Console, APIs, or SMTP.

Amazon Pinpoint

  • Scalable two-way marketing communications (email, SMS, push, voice, in-app); segment and personalize; receive replies; scale to billions; send to SNS/Firehose/CloudWatch Logs.
  • Unlike SNS/SES (you manage each message/schedule), Pinpoint manages templates, schedules, segments, and full campaigns.

Systems Manager (SSM)

  • Session Manager — secure shell to EC2/on-prem with no SSH, no bastion, no port 22; Linux/macOS/Windows; logs to S3/CloudWatch.
  • Run Command — run a document/command across instances (no SSH); output to Console/S3/CloudWatch; status to SNS; IAM + CloudTrail integrated; invocable via EventBridge.
  • Patch Manager — automate patching of EC2 and on-prem; on-demand or scheduled via Maintenance Windows; compliance reports.
  • Maintenance Windows — schedule, duration, registered instances, registered tasks.
  • Automation — common maintenance/deployment (restart instances, create AMIs) via Runbooks; triggered manually, by EventBridge, by Maintenance Windows, or by AWS Config remediation.

Cost Management

  • Cost Explorer — visualize/manage cost over time; custom reports; granular (hourly/by resource); choose optimal savings plans; forecast.
  • Cost Anomaly Detection — ML to find unusual spend vs history; alerts via SNS (individual or summaries).

AWS Outposts

  • Server racks bringing AWS infrastructure/services/APIs on-premises; AWS sets up and manages them; benefits: low latency, local processing, data residency, easy migration, fully managed.

AWS Batch

  • Fully managed batch processing at any scale (100,000s of jobs); jobs have a start and end; dynamically launches EC2/Spot; provisions compute/memory for you; jobs are Docker images run on ECS. Not serverless and no time limit (a "heavier Lambda").

Amazon AppFlow

  • Managed integration to securely transfer data between SaaS apps and AWS. Sources: Salesforce, SAP, Zendesk, Slack. Destinations: AWS services (S3). Scheduled/event/on-demand; data transformation; encrypted over the public internet or via PrivateLink.

AWS Amplify

  • Tools/services to build and deploy scalable full-stack web/mobile apps — one place for auth, storage, API, CI/CD, PubSub; connect source from GitHub/CodeCommit/Bitbucket/GitLab or upload. ("Elastic Beanstalk for web and mobile apps.")

Instance Scheduler on AWS

  • A CloudFormation solution (not a service) that auto-starts/stops resources to save cost (e.g., stop EC2 outside business hours); schedules in a DynamoDB table; uses tags + Lambda; cross-account/Region.
