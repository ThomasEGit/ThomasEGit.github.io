AWS Cloud Video Processing

Reducing video processing time with distributed computing.

StatusCompleted
Year2026
StackC++, CUDA, FFmpeg, S3, SQS, DynamoDB, EKS, KEDA, Karpenter

Introduction

This all started because I wanted to apply cool effects on video files and have it be very fast. I fell down a rabbit hole while researching and I now understand why this is a whole industry. The goals of the project were to:

  • Process the video as fast as possible.
  • Handle several videos needing to be processed at the same time.
  • Apply a VHS effect to a video file.

This page will document things I learned while accomplishing these goals, reasoning for the architectural choices, and the results.

Processing a Video Fast

Before actually applying the effects, we need to understand the basics of a video processing pipeline. For the project specifically, I have these video processing stages:

  • Demux stage to find basic information about the input file like if there is a video stream.
  • Decode stage to create a decoder that is used to decompress video packets into frames.
  • Process stage where every frame has its luminance and chrominance planes modified.
  • Encode stage to turn the frames back into compressed video packets.
  • Mux stage to write back into the container.

The decode, process, and encode stages are the most computationally heavy because decode and encode will run on every single frame which can be in the tens of thousands depending on the frame rate and length of the video. The process stage can be expensive too depending on how many pixels are modified and the complexity of the effect algorithms. Luckily, GPUs have dedicated hardware encoders and decoders as well as CUDA cores that can be used to reduce the time it takes for these 3 stages. This project uses FFmpeg to build all stages of the pipeline and setup the GPU hardware to properly use NVDEC for decoding and NVENC for encoding. For the processing stage, the single threaded effects were converted to custom CUDA kernels. With these 3 changes, a 4K 60FPS 4 minute video with 4 effects applied went from 1.25 hours to under a minute to process.

One quick note about this benchmark is that adding or removing effects didn't linearly change the processing time on the CPU. Some effects were much heavier than others and adding them made a noticeable increase to processing time on the CPU end. On the other hand, when applying the same effects in CUDA there was barely any change to the processing time which makes the speedup between CPU and GPU increase as we keep adding effects.

Handling Several Videos for Processing

I noticed that when running the program on my own system, the GPU was nearly maxing out and if I had other tasks using my GPU the processing time was slower. Additionally, processing multiple videos at the same time was not possible which meant I had to wait for one process to finish to start another. Ultimately, how much I could process and how fast were limited so I leaned into my AWS knowledge to shift to a cloud distributed compute design. Shifting the workload to the cloud sounds simple, but there is a new list of tasks/goals which are:

  • Store videos somewhere every worker can reach.
  • Break long videos into chunks and process them in parallel across many workers.
  • Handle failures gracefully, since workers and instances can die.
  • Scale the number of workers and keep costs low.

Being able to upload and download videos was probably the easiest part. AWS has two main storage options and they are AWS S3 buckets or AWS elastic block storage (EBS), each having its own pros and cons. AWS S3 bucket objects can be accessed by any worker in any AZ, have storage capacity well beyond our needs, and S3's pricing model works well for our burst workloads. The main factor though is that the short lived EC2 GPU instances need to have access for reading and writing to the same location which isn't possible with EBS volumes. EBS volumes do have low latency since they're attached to EC2 instances, but it won't help us for our use case and for these reasons AWS S3 buckets will be used.

If a very long video (2 hours) is sent into a GPU instance for processing then that GPU instance owns that task until completion. In this scenario, one GPU instance sits at max or near max utilization while others are idle and if processing errors occur later then compute time would have been wasted to reach the error. This design is not ideal and the videos can be processed with much better efficiency and scalability by using Amazon Simple Queue Service (SQS) and Amazon DynamoDB.

Instead of one large task, the video is broken up into chunks of ~30 seconds if the video is longer than 1 minute and 30 seconds. Broken up chunks are tagged with a job ID and stored back into a temporary section of the input S3 bucket. Each chunk is then sent to an SQS queue where the GPU instances can scale up or down based on queue length.

The job IDs prevent the program from mixing chunks from other videos together and DynamoDB will track how many chunks for a video are left. As workers finish chunks, they decrement that video's counter in DynamoDB and the worker that brings the counter to zero will perform the final stitch that reassembles the chunks into one output video.

One concern is that SQS can hand the same chunk to two workers and count them twice. This will make the counter hit zero early and stitch an incomplete video with no error to show for it. To avoid that, each job's row keeps a set of the chunks it has already recorded, and a chunk that is already in that set is ignored.

Workers can crash mid-chunk, spot GPU instances can be lost, and chunks can fail to process, so the program has to recover gracefully and still produce the final video. SQS handles the issue of failed chunks being lost because the chunk is only deleted from the queue if an instance fully processes it. If a chunk fails then it will just reappear in the queue and be processed again. More importantly, that means the video's chunk counter decrement in DynamoDB must occur after it is actually successfully processed. There are also chunks that could just fail no matter what and those are moved into a dead-letter queue to prevent wasting more compute and clogging the queue.

The final task was to scale workers correctly and keep cost low. By using Kubernetes Event-driven Autoscaling (KEDA), the number of worker pods is scaled up based on SQS queue length. Amazon Elastic Kubernetes Service (EKS) can manage which worker pod runs on which GPU instance and the instances can be scaled up from zero by Karpenter. This design will ensure that for high throughput there will be enough resources ready to process, and for low throughput any idle GPU instances are taken down to save cost.

VHS Effects

This part of the project was rather tricky because there isn't a common consensus to what VHS effect should look like, CRT televisions added their own effect to the display, and I personally don't remember what VHS tapes were like nor have access to one. I looked at online resources and these effects commonly appeared:

  • Horizontal scanlines.
  • Chromatic bleed.
  • Chromatic aberration.
  • Noise/Static.
  • Tape damage.
  • Tearing.

There is nothing too special about the algorithms to incorporate these effects, but the type of data that came from decoded frames was interesting. After decoding, the application gave back 1 luminance and 1 chrominance plane, but the chrominance plane is interleaved. For readability, I decided to split up the planes, apply the effects, and interleave them back together. Deinterleave and interleave is pretty straightforward, but there is a neat technique used to access the element we want. The planes from a frame are given to the application as an unsigned 8 bit int pointer which means doing a [][] accessor isn't possible. It is a flattened 2D array which means that the row or y multiplied by the stride plus the column or x will give you the pixel you want.

Scanlines were the most common effect I saw that gave a VHS feeling and it is just an effect that came from CRT TVs. Visually looking at the effect, it is just a simple darkening of a row in an interval which means that the luminance frame or Y frame must be modified.

Both the chrominance effects above were the second most common effect I saw and they are pretty simple effects. ChromaBleed(...) and ChromaAberration(...) are where color would spread outside of the expected area. What is most interesting is that I couldn't use std::clamp here because these functions run on the GPU and the standard library isn't available in device code. It would be wasteful to import all of std into the GPU so I had to use max and min to clamp which are GPU functions.

If you wanted to make your own VHS effect, then I would say that copying the functions above would give you the bare minimum in achieving that VHS effect for your project.

Results

I've been writing a lot and it has been hard holding back all the cool things I found. To reward readers, here is the final product with many effects applied to get as close as possible to a VHS tape.

Processing both of these videos only cost cents and the total cost of this project including debugging was roughly $9. Admittedly about $3 came from me trying to wait for a GPU spot instance to come up and having to switch to on-demand GPU instances instead. What is nice about the design is that this can be expanded to more than just applying VHS effects to a video. The current design has it that any video processing can be performed on input files, but I had to stop myself before extending this project to a year long one.

Something fun to note is that the file size has significantly changed after applying the effects. The bird video went from 65 MB to 255 MB and I only uploaded about ~100 MB of video for the VHS version. It turned out that when the video had those effects applied there were far fewer predictable frames. Videos are compressed to I, P, and B frames where the P and B frames are predicted frames. The main issue is that fewer pixels are predictable because of all the noise and effects I added which made those frames bigger and the total file size bigger.

If you're wondering why the audio stream is missing, it is not a problem on your end. It was my own intentional choice to drop the audio stream since I really wanted to focus on the video data.
